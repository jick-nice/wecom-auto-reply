# 企业微信自动回复 / 抢单助手

这是一个面向 Windows 的企业微信群消息自动回复工具：通过屏幕截图和 OCR 识别聊天区域中的新消息，识别派单人、数字口令和指定手势后，自动向企业微信输入并发送对应回复。项目不读取企业微信进程内存，也不注入企业微信进程；主要使用 Win32 截屏、RapidOCR 和键盘输入完成自动化。

适用场景包括群内抢单、固定数字口令回复、手势派单识别和企业微信消息自动化测试。当前版本包含比耶手势识别、跨 DPI 窗口定位、OCR 结果缓存、启动基线去重、F9 启停和跨电脑抓帧失败自动重试。

## 项目结构

- `client_v33/`：当前客户端入口、运行时补丁、OCR 和手势识别逻辑
- `client/`：早期客户端源码和诊断工具
- `backend/`：可选的管理后台与 Supabase 数据库结构
- `tests/`、`client_v33/tests/`：识别、启动交互和跨电脑抓帧回归测试
- `samples/`：本地识别回归图片
- `assets/`、`client_v33/assets/`：图标和手势模板
- `build.py`：PyInstaller 打包脚本

## 快速开始

1. Windows 安装 Python 3.11，并安装项目依赖。
2. 运行客户端源码入口：

```powershell
python client_v33/main.py
```

3. 首次运行后在本地配置中填写后端地址、派单人和自己的群昵称。配置文件位于 `%APPDATA%\\AutoGrab\\config.json`。
4. 登录企业微信并打开目标群聊，在助手中点击“开始抢单”，也可以使用 F9 启停。

## 一、为什么彻底放弃"手工框选"

老版本让用户拖一个矩形，本质是把 **Tk 的逻辑像素** 当成屏幕物理像素用。
在同事那台 Win7 + 125% 缩放的机器上，逻辑像素和物理像素差一个小数倍，
拖出来的框整体偏移并缩小 → **一个字都认不出来**，这就是当初失败的原因。

v3.1 的坐标来源**只有一个**：`GetClientRect` + `ClientToScreen`（Win32，物理像素）。
用户不再提供任何坐标。聊天区是在窗口内部靠结构自动认出来的：

```
① 找输入框上边框 —— 横贯面板的一条 1px 线，且上下两侧都更亮
   （气泡填充也偏暗，但气泡"下面"不亮，所以不会被误判）
   实测命中 y=606，左右端 x=327..883
② 由输入框左右端反推聊天面板的左右分隔线   → x=310 / x=919
③ 向上找群名 header 的底线               → y=63
④ 消息区 = (310,64)-(919,604)
⑤ 自校验：在这个区里切行，能配出「名字行 + 气泡行」才算成功
```

窗口移动、缩放、换分辨率、换显示器、改 DPI：**每帧比对客户区矩形，变了就重算**，用户无感。

`client/diag.py` 就是给这件事做现场取证的：在任何机器上跑一次，输出
Windows 版本 / DPI 模式 / 客户区物理矩形 / 两条抓屏路径的定位结果 / 真实 OCR 结果，
并保存一张红框标注图。**换机器出问题时，跑它、把图和文本发回来即可。**

## 二、实测数据（本机企业微信 4.x，1080×760 窗口）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 自动定位 | **24ms** | 只在启动/窗口变化时跑一次 |
| 抓帧·前台 | **4ms** | BitBlt 只抓消息区 |
| 抓帧·后台 | **16ms** | PrintWindow，窗口被遮挡也能抓 |
| 切行 | **1.4ms** | 540×609，双锚点已学 |
| 稳态单帧 | **1.4ms** | 内容没变 → OCR 全命中缓存 |
| 新派单冷启动 | **7~20ms** | 单数字 7.5ms；带 emoji 的「宜居园 3️⃣」20ms |
| 发送 | **10ms** | 打字（数字）→ 回读输入框确认 → 回车 |
| **端到端** | **≈30~60ms** | 从消息出现到答案发出 |
| **端到端（带校验）** | **108ms** | 真机实测：`⚡ 抢单 → 发送108ms`，含回车后回查确认 |

最后一轮真机验证（`tools/live_reply_e2e.py`，真实企业微信群、真实键盘输入）：

```
🧱 启动基线：当前 4 条已有消息记为已处理（不会去回旧单）
→ 群里出现一条新消息
[eng] ⚡ 抢单 → 「99」 发送108ms 总计108ms
--- 最后几条 ---
   [(我)] '3'
   [(我)] '4'
   [(我)] '99'          ← 自动回出去的
```

真实窗口的识别结果（`client/diag.py` 输出）：

```

1. [悲伤土豆] '大家好！我是悲伤土豆，我来了。'   (135ms 首次)
```

## 三、这次在真机上踩掉并修掉的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| ClearType 彩色描边 | 整行文字被判成 emoji 徽章，每帧多跑 2 次 rec（44ms/帧） | 4×4 池化 + `sat>90` + 实心度&长宽比校验，现在零误判 |
| **画面静止 → 永远不回单** | 派单进来后画面就不动了，"连续两帧确认"等不到第二帧，**真实派单躺在群里没人回** | 看到候选派单就记一个"补看一眼"的时限，画面没变也再跑一次（60ms 后） |
| **一启动就去回旧单** | 启动时画面最后两条被当成刚到的派单 | 启动基线：先把画面上已有消息记为已处理 |
| **中文输入法吃掉字母** | 想发 `garden3`，被吃成候选字 `暗grdengarden`，回车还被拿去确认候选 | 回复**只发数字**（数字不经过候选）；回车后回查输入框是否变空，没空就再按一次 |
| 输入框残留 | 框里还剩一个 `9`，再打一个 → 消息变成 `99` | 发送前先探测（暗像素 > 120 视作有草稿，不动它） |
| 名字行只切到笔画中段 | 12px 灰字被切成 6px 高，`悲伤土豆` 读成 `非伤十豆` | 名字行 OCR 上下补 6px 边距，8 种缩放组合全部读对 |
| 短聊天是**顶部对齐** | 只盯底部条带 → 空群/刚开群时完全看不到最新一条 | 处理整个消息区（PrintWindow 反正整窗渲染，成本不变） |
| 徽章与文字重复 | `宜居园3 3` | rec 自己就能把 `3️⃣` 读成 `③`，号码归一化后是同一个 3 |
| 后台窗口截不到 | 必须让微信在前台，一用电脑就瞎 | PrintWindow 后台渲染，**不抢焦点**也能抓 |
| 鼠标被抢走 | 每次发送都把光标甩到输入框 | 点完立刻把光标放回原处；能不打字就不点鼠标（见第四节） |
| 输入框校验读不出来 | 输入框里的字只有 10px 高，OCR 把 `4`/`7` 全读成空 → 误判「没收到」 | 改成数**相对背景的暗像素**（空框 0、打一个数字 22），0.3ms |
| 亮度公式溢出 | `int16` 下 `255×150=38250` 溢出成负数，读数恒为 -1 | 全部改 `int32`，并在注释里标了这个坑 |
| 屏幕抓取抓到别的窗口 | 企业微信在后台时 `BitBlt` 抓到的是压在上面的控制台 | 探针也遵循「前台抓屏 / 后台 PrintWindow」，并按背景中位数自适应深浅主题 |
| 探针读到全黑 | 探针和主循环共用同一个 `Grabber`（同一块 DIB），两个线程互相踩 → 误判「字没进去」把刚打的字退格删掉 | 探针单独用一个 `Grabber` |
| 手机 adb 点不动企业微信 | `input tap` 在**顶部工具栏、底部标签栏**有效，在**聊天列表行、发送键**完全无效 | 企业微信内容区会丢弃注入的触摸事件（非 root 无解），群发消息只能人工在手机上点 |

### 4.1 口令解析：该认的认，不该认的死活不认

| 必须认出来 | 结果 |
|---|---|
| `正荣府扣2` `正荣府2` `正荣府 2` `正荣府　2`（全角空格） | 2 |
| `2️⃣` `②` `❷` `三` `叁` `參` `叄` | 2/3 |
| `双街新家园 看房叁` `看房叁` `定房贰` | 3 / 3 / 2 |
| `ZHENGRONGFU2` `ZhengRongFu8` `A-3` `B3`（大写/编号） | 2 / 8 / 3 / 3 |
| `89平 3号楼 扣2` `正荣府 2室2厅 扣3`（多数字里抓「扣」） | 2 / 3 |
| `正荣府（二期）扣4` `正荣府：扣5` `【急】正荣府 扣7` | 4 / 5 / 7 |

| 必须无视（返回 None） | 为什么 |
|---|---|
| `前三名` `排名3` `第3个` | 序数/排名 |
| `3天` `3小时` `3成` `3岁` `3次` `3个` | 量词 |
| `89平` `89平米` `3万` `扣1万` `价格3万5` `首付3成` | 面积/价格（`3万5` 里那个 5 属于同一个价格） |
| `3-5` `3~5间` `3至5套` `2-3间` | 区间 |
| `9:30` `3.5` `1/3` `v2.1` `2024-06-01` | 时刻/小数/分数/版本/日期 |
| `13800138000` `1234567` | 手机号/长编号 |
| `一共3个人` `明天3点` `三室两厅` `一共三套` | 句中量词（中文字数字只在行尾才算数） |
| `3号楼` `2单元` `2号线` `3室` `3楼` | 房号/单位 |

> 关键一条：**中文字数字（三/叁/两）只有落在行尾、紧跟房源名时才算口令**，
> 因为它出现在句中多半是量词（"一共三套"、"三室两厅"）。

### 4.2 显示设置：把真实截图做各种蹂躏，还认得出

拿真机截图当素材，做 20 多种变换，每种都要求"仍然认出 朱洋 → 宜居园3 → 3"：

| 变换 | 覆盖的真实场景 | 结果 |
|---|---|---|
| 缩放 0.5 / 0.6 / 0.75 / 0.9 / 1.1 / 1.25 / 1.5 / 2.0 / 3.0 | 系统缩放 100%~300%、窗口拉大拉小、不同分辨率 | 全过 |
| 亮度 0.6 / 0.75 / 0.85 / 1.15 / 1.3 / 1.5 | 屏幕调暗、调亮、夜间模式 | 全过 |
| 对比度 0.6 / 0.75 / 1.3 / 1.6 | 显卡/显示器对比度、护眼模式 | 全过 |
| JPEG 质量 40 / 70 | 远程桌面、投屏、视频流编码损耗 | 全过 |
| 高斯模糊 0.5 / 1.0 | 缩放插值、非整数缩放 | 全过 |
| **整帧反色** | **深色模式 / 高对比度主题**（深底浅字） | 全过 |

为此改了三处：

1. **阈值不再写死 150**，改成跟着背景亮度走（比背景暗 30 就算字）。
   原来屏幕一调亮，浅灰的名字行（#999→#C7）就整行消失 → 派单人认不出来 → 直接漏单。
2. **行间距跟着画面尺度走**（`max_gap = max(50, 中位行高 × 2.4)`）。
   原来固定 50px，整屏 200% 缩放时名字行和气泡配不上 → 所有人都变成"无名字"。
3. **深色模式整帧反色**（背景中位亮度 < 110 时 `255 - frame`），
   否则投影切行和 OCR 全部失效（实测：不反色一行都切不出来）。

### 4.3 干扰消息：贴纸、图片、系统消息、别人发的数字

合成一张"脏"聊天图（系统消息 + 别人发的 `3` + 贴纸色块 + 图片 + 派单人正常派单）：

```
识别结果：[('', '悲伤土豆 加入了群聊'), ('于超凡','3'), ('','王琦'), ('','o'), ('','[图片]'), ('朱洋','宜居园3')]
```

- 贴纸/(图片) 认出来是空文本或 `[图片]` → `reply_code` 返回 None → 不回
- 别人发的 `3` 认得出，但**不在派单人名册里 → 不回**
- 派单人那条照常认出 → 回 3

引擎级还要过一道：把这张图连续喂 3 帧给 `Engine._judge`，
**必须只发出一次 `3`**（别人发的数字一条都不能触发）。

### 4.5 这一轮又踩出来的 4 个坑

| 坑 | 症状 | 修法 |
|---|---|---|
| **画面刚变的那一帧是"半张"** | 企业微信先画时间分割线、后画气泡，引擎判完这帧画面就再也不变了 → **真派单整条漏掉**（实测漏了 5 条） | 任何画面变化后 **70ms 无条件再判一次**；同时判最后 3 条而不是 2 条 |
| **时间分割线和气泡并成一行** | OCR 读出 `上午2:32: 4`，数字被当成口令 | 解析前先剥掉行首的 `上午/下午/昨天… H:MM` |
| **输入框残留拼成"22"** | 上次没清干净剩个 `2`，这次又打 `2` → 群里出现 `22` | 探针发现框里有少量残留（>6 个暗像素）先退格清掉再打 |
| **自己回出去的气泡被配上派单人的名字** | 自己的 `2` 被当成新派单 → 理论上会无限自激回 | 自己发的气泡一律不判（`self_dispatch` 默认 false，只在测试工具里打开） |

## 五、企业微信风控：为什么弹「设备环境异常」，以及现在的防护

**没有注入、没有 hook、没有读企业微信内存。** 全程只有两条通道：外部抓屏（`PrintWindow` / `BitBlt`）
+ 系统级 `SendInput` 打字。UIA 也探测过，WeCom 4.x/5.x 只对外暴露 `TitleBarWindow`/`PerryShadowWnd`，
内容树根本拿不到，想注入也没有着力点。

那弹窗从哪来的？做了差分实验（`tools/risk_probe.py`）：

| 实验 | 动作 | 结果 |
|---|---|---|
| A | `PrintWindow` 连续抓 192 帧 / 200 秒，**零输入事件** | 全程不弹，账号正常 |
| B | 同一坐标连点 5 次 + 连敲 10 次键 | 几分钟内弹「需通过手机企业微信扫码进行安全验证」 |

结论：**触发源是「模拟输入的量」，不是抓屏。** 企业微信会检测 `SendInput` 产生的
`LLMHF_INJECTED` 鼠标事件，短时间高频、或反复戳同一个点，是典型机器特征。

### 五层防护（按发生顺序）

1. **零点击优先**：正常情况一次鼠标都不点；只有"打完字发现输入框没进字"才补点一次。
2. **点击硬上限**：整个会话最多 3 次（`max_clicks_per_session`），点完光标立刻归位。
3. **不在前台就不发**：企业微信被别的窗口挡住时这一单直接不发，界面置顶提示「手动回 X」，
   **绝不抢焦点**。抢焦点原来靠模拟按一下 Alt，已删掉，改成 `AttachThreadInput`（纯状态切换，
   不产生任何输入事件）。
4. **不再盲打**：打字后立刻回读输入框（暗像素计数，0.3ms），确认字真的进去了才按回车；
   没进去就退格清掉、放弃这一单——宁可不发，也不盲按回车吐一条错的。
5. **草稿保护**：输入框里有别的草稿，直接不动。

### 万一还是弹了

1. 账号**不会掉**，手机上扫码验证即可恢复（实测不处理也会自动超时恢复）。
2. 弹窗时聊天区结构会消失，软件每 30 秒做一次结构体检，发现异常只**记日志提示**，不会去点那个页面。
3. 想更保守：把 `config.json` 的 `allow_click` 改成 `false`，从此只打字、不点鼠标，
   代价是每次得你先手动点一下输入框。

## 六、判定链（按你的规则）

```
派单人发「房源名 + 口令」     → 立刻回声口令（同一单只回一次，30s 内去重）
派单人随后 @ 的第一个人       → 就是抢到这一单的人
        @ 的是我              → 今日 +1，到 3 单自动停止
```

- 派单人用 5 个名字模糊匹配（去括号备注、包含关系、相似度 ≥0.72）。
- 「口令」解析见 `client/app/numparse.py`：`3️⃣` `③` `❸` `叁/參/叄` `扣2` `扣伍`
  `89平 扣3` `3号楼 扣1` `看房叁` 全部归一成数字，`前三/排名/3万/3号` 这类噪声会被排除。
- 同一内容连续两帧读到才发（防半截渲染误判）。

## 八、换机器/换分辨率怎么搞

- **什么都不用做**。定位自动重算，锚点自动学习。
- 只有在定位失败（日志出现 `⚠️ 没能识别出聊天区结构`）时，才点 **手动兜底** 拖一次区域 ——
  拖出来的坐标会**立刻换算成相对窗口客户区的坐标**存盘，之后再换分辨率也不会错位。
- 到新机器先跑 `python diag.py`，把 `diag_overlay.png` 和 `diag_result.txt` 发回来。

## 十、安全边界

| 做的事 | 是否触碰企业微信 |
|---|---|
| PrintWindow / BitBlt 抓像素 | ❌ 和截图软件一样 |
| SendInput 敲 1 个数字 + 回车 | ❌ 和键盘/AutoHotkey 一样 |
| SetThreadExecutionState 防休眠 | ❌ 进程自身 API |
| 注入 DLL / hook / 读内存 / 改客户端 | **完全没做** |

进程里不出现任何企业微信模块，不给它任何可检测的注入点。代价是：打字时必须让企业微信拿到前台焦点
（所以发现没进字才补点一下输入框，点完把鼠标放回原处）；抓屏则后台也能进行。

风控这块经过差分实验：**抓屏不触发、模拟输入才触发**（详见第四节）。所以策略是
"能不打字就不打字、能不点就不点、点有硬上限、不在前台就不发、发之前先确认字进了框"。
